# Призывы «как в Path of Exile 2»: анализ и план реализации

Статус документа: **исследование + план (2026-11-11)**. Реализованы и ждут полевого теста: M0, M1, M2, M3 (базовый набор действий), M4, M5 (строй + исследование лимита), M6 (отображение); M7 — нет. Факты о PoE2 собраны из PoE2 Wiki и форумов разработчика/игроков (ссылки в конце); точные числа PoE2 меняются от патча к патчу и здесь служат ориентиром, а не требованием.

## 1. Как устроены миньоны в PoE2

| # | Механика PoE2 | Что видит игрок |
|---|---|---|
| P1 | **Постоянные миньоны** (persistent): живут, пока активен навык, резервируя ресурс (Spirit), а не по таймеру | армия всегда рядом, её не нужно перепризывать каждые 60 с |
| P2 | **Авто-возрождение**: погибший постоянный миньон возвращается сам через ~7 с, если другие союзные миньоны не умирали недавно | смерть миньона — временная потеря, а не конец билда |
| P3 | **Плотное следование**: миньоны держатся рядом с игроком, при отставании бегут, при большом отрыве телепортируются к нему | армия не теряется и не «застревает» позади |
| P4 | **Дальность агрессии**: миньоны сами атакуют врагов в некотором радиусе от игрока; у некоторых видов агрессию можно настроить в меню навыка | игрок управляет билдом, а не каждым миньоном |
| P5 | **Командные навыки (Command)**: у части постоянных миньонов есть особое действие по команде игрока — кладётся на панель вместо самого миньона (например, «рвануть к цели и взорваться», «создать взрыв в точке и оставить клона») | активное управление: «вы — туда, ты — взорвись» |
| P6 | **Приоритет цели игрока**: миньоны концентрируются на том, по кому бьёт/кого указывает игрок | фокус по опасной цели |
| P7 | **Количество**: десятки миньонов одновременно, лимит задаётся навыком/ресурсом | ощущение армии |
| P8 | **Интерфейс**: значки миньонов со здоровьем и таймером возрождения | видно, кто жив, кто возрождается |
| P9 | **Взаимодействие навыков с миньонами** (жертвы, баффы, «предпочитать миньонов этого навыка»), настройка «не позволять навыкам-жертвам целиться в миньонов» | синергии билда |

Известные слабости PoE2, которые копировать не нужно: игроки жалуются, что ближние миньоны застревают и не проходят даже по команде, и просят режим «пассивные, пока не прикажу».

## 2. Что уже есть в SCF и чего не хватает

| PoE2 | SCF сейчас | Вердикт |
|---|---|---|
| P3 следование | `Follow` keep-offset в слотах строя, `Return`, аварийный warp | **есть, но конфликтует с ванильным пакетом следования** (см. §3) |
| P4 агрессия | `Passive`/`Defensive`/`Aggressive`, `CombatGate` запрещает бой в `Passive`/`Return`/`MoveTo` | есть режимы; нет **радиуса агрессии вокруг игрока** |
| P5 команды | `FocusTarget`, `MoveTo`, `Guard`, `Return`, `Follow` | общие команды есть; нет **индивидуальных командных действий** по типу призыва |
| P6 фокус | `FocusTarget` + пин цели в селекторах `CombatController` (поле подтвердило `answered with focus`) | есть; нет **«бей того, кого бью я»** автоматически |
| P1 постоянство | — (ванильная длительность заклинания) | **нет** |
| P2 возрождение | — | **нет** |
| P7 количество | реестр до 32, ванильный лимит 1/2 (Twin Souls) | **нет** (лимит движка не тронут) |
| P8 интерфейс | HUD-сообщения, меню FLICK | **нет панели миньонов** |
| P9 синергии | защита от дружественного огня (FF-01) | частично; остальное — вне ядра |
| — проход сквозь друг друга | физика: `bEnableSummonToSummonBypass`; планировщик: TODO в PLAN.md (этап 2) | **частично** |

## 3. Блокер №1: призыв не принадлежит SCF полностью

Пока любой из этапов ниже строится поверх ванильного ИИ призыва, он будет «прерываться по какой-то причине» — ровно то, что видно в поле при `MoveTo`.

* **Факт (1.5.97):** id 36410 (`+5DBA80`) строит каждому призыву runtime-пакет (тип 18, FormID `0xFF…`) из шаблона `FollowTo` с `Min Radius = fSummonedCreatureMinFollowDist` (200). Этот пакет всё время тянет призыва к игроку.
* **Поле 2026-11-11 00:08–00:13:** отпуск поводка (`FollowLeash`) **ни разу не сработал**: у экземпляра `templateParent = 0` (`[Leash] ... type 18, template 0x00000000 ... not released`), а проверка требовала `templateParent == FollowTo`. Волки продолжили прерывать `MoveTo` (за сессию 1 прибытие из нескольких приказов).
* **Что нужно (этап M0):** опознавать пакет не по `templateParent`, а **по факту создания**: перехватить вызов `+5DD030` внутри 36410 (call-site patch, как у `CombatGate`) и запомнить «призыв → созданный пакет»; либо, как запасной путь, принимать runtime-пакет типа 18 с ровно двумя `BGSPackageDataFloat` и целью-владельцем. Затем — либо отпускать радиусы, либо заменить управление движением целиком (M1).

## 4. Можно ли сделать «как в PoE2»

**Да, по большей части — но как Skyrim-версия, а не копия.** Ограничения движка:

* **Да, реализуемо:** постоянные призывы и авто-возрождение (P1, P2), плотное следование с бегом и телепортом (P3, при условии M0), радиус агрессии и «бей того, кого бью я» (P4, P6 — всё на уже готовых `CombatGate`/`TargetPin`), командные действия через заклинания/атаки самого призыва (P5), панель миньонов в ImGui через FLICK (P8), резерв магии вместо Spirit (P1).
* **Частично:** количество (P7). Лимит призывов задаётся движком (Twin Souls поднимает до 2); поднять его выше — отдельное исследование. 6–10 одновременных существ реалистичны, 30+ как в PoE2 — нет: в Skyrim каждый актор — полноценный ИИ с навмешем, анимацией и физикой, это бьёт по производительности и по пути в узких местах.
* **Нет / не стоит:** изометрическая «рой-логика» PoE2 без навмеша, мгновенные развороты и пролёт сквозь всё — Skyrim двигает актёров по навмешу с анимационной локомоцией. Цель — «быстро, плотно, без застреваний», а не пиксель-в-пиксель.
* **Главный риск:** всё держится на M0. Без полного владения движением и боем любая надстройка будет конфликтовать с ванильным ИИ.

## 5. План реализации

Каждый этап — отдельные пункты в PLAN.md, отдельный коммит, unit-тесты чистой логики в `src/Core`, полевой тест пользователем. Порядок важен: M0 → M1 обязательны, дальше можно параллелить.

### M0. Полное владение движением призыва (блокер)
**Статус 2026-11-11:** реализовано (seat на создании `+5DBB04` для SE 1.5.97 + опознание по форме), ждёт полевого теста. Подробности — PLAN.md, этап 3.
* Перехват создания пакета следования (call-site у `+5DD030` в id 36410, проверка по дизассемблеру и SE/AE ID), реестр «призыв → пакет».
* Отпуск/восстановление радиусов по найденному пакету; лог «нашли/отпустили/вернули».
* Наблюдение в поле: `MoveTo` в 700–2000 ед. без остановок и разворотов к игроку.
* Если радиусы не перечитываются на лету — запасной путь: `EvaluatePackage` после записи, либо подмена ответа о текущем пакете для управляемых призывов (как APMF ch.9, только для нашего призыва).
* **Готово, когда:** 10 из 10 `MoveTo` подряд заканчиваются `arrived at MoveTo point`, без `[Leash] not released`.

### M1. Следование как в PoE2
**Статус 2026-11-11:** реализовано, ждёт полевого теста. Три темпа (`core::DecideFollowMotion`): шаг ≤ `fFollowMaxDistance`, бег, рывок > `fSprintDistance` (1200) — через временный модификатор `SpeedMult` (100/160/230) с точным откатом; телепорт за спину только в `Follow`/`Return` вне боя — по `fCatchUpDistance` или после `fStuckWarpSeconds` (3 с) без прогресса при отставании > `fStuckWarpMinDistance` и почти нулевой скорости, не чаще раза в 5 с. Рывок меняет скорость, а не набор анимаций. Проход сквозь друг друга сделан раньше (PassThrough).
* Плотный строй вокруг игрока (уже есть) с тремя скоростями: шаг в строю, бег при отставании > N, рывок (sprint) при отставании > M; телепорт за спину при > `fCatchUpDistance` или застревании (есть, расширить на «нет пути»).
* Призывы не обходят и не толкают друг друга (TODO этапа 2 PLAN.md: avoidance в планировщике).
* **Готово, когда:** при беге игрока по лесу 4 призыва держатся в строю, ни один не отстаёт больше чем на 2 с, нет «танцев» друг вокруг друга.

### M2. Агрессия и цели как в PoE2
**Статус 2026-11-11:** реализовано «бей того, кого бью я» (`TESHitEvent` → FocusTarget) и радиус агрессии вокруг игрока для боёв, выбранных движком; ждёт полевого теста. Не сделано из этапа: выход из уже идущего боя, когда враг уводит призыва за радиус (сейчас это делает существующий combat leash по дистанции до игрока).
* `fAggressionRadius` (INI/FLICK): в `Defensive`/`Aggressive` призыв вступает в бой только с врагами в радиусе от **игрока**, а не от себя (правило в `core::CombatPolicy` + проверка в `CombatGate`), и выходит из боя, если враг уводит его дальше (`combat leash` уже есть — согласовать).
* «Бей того, кого бью я»: `TESHitEvent` с агрессором-игроком → `FocusTarget` по жертве для всего отряда (с таймаутом), без нажатия клавиш; настройка вкл/выкл.
* Режим «пассивные, пока не прикажу» — уже есть как `Passive` + Focus; проверить сценарий.
* **Готово, когда:** игрок бьёт врага — все призывы переключаются на него в течение 0.5 с; враг за пределами радиуса агрессии не атакуется, пока не подойдёт.

### M3. Командные действия по типу призыва
**Статус 2026-11-11:** реализовано (клавиша `Numpad 7`, каталог `SummonControlFramework_Commands.ini`, действия `Rush` / `CastAtTarget` / `Detonate`, кулдаун на призыва), ждёт полевого теста. Отличия от исходного замысла: `Rush` — это Focus + временная прибавка `SpeedMult`, **без силовой атаки** (запуск силовой атаки на графах существ не исследован); `Taunt` не сделан; клавиша действует на всех призывов игрока, выбор «под прицелом» — вместе с панелью M6. Ключ каталога — база призыва (с цепочкой шаблонов и `ExtraLeveledCreature`), строка `Default` — для всех остальных.
* Данные: `SummonControlFramework_Commands.ini` — `база призыва (Plugin|FormID) → команда`: `Rush` (рывок к цели с силовой атакой), `CastAtTarget` (заклинание от лица призыва в цель/точку, `MagicCaster::CastSpellImmediate`), `Detonate` (взрыв-заклинание + отзыв призыва), `Taunt`.
* Отдельная клавиша «Command» (FLICK-бинд): исполняется для призывов под прицелом/всех; кулдаун на тип.
* Только существующие записи игры/мода, без ESP; безопасный отказ, если запись не найдена.
* **Готово, когда:** для огненного атронаха «Command» по цели кастует огненный шар в неё, для волка — рывок с атакой; кулдаун и лог работают.

### M4. Постоянные призывы и авто-возрождение
**Статус 2026-11-11:** реализовано (`core::Persistence*`, `engine::persistence`), по умолчанию выключено (`[Persistence] bPersistentSummons = false`), ждёт полевого теста. Отслеживается любое заклинание с эффектом Summon Creature, скастованное игроком (мод-призывы тоже), кроме чёрного списка `sBlacklistedSpells`; `bPersistVanillaSpellsOnly` сужает до заклинаний из официальных мастеров (по исходному файлу записи). Возрождение — `CastSpellImmediate` от игрока с целью «игрок» (как штатно появится призыв с доставкой Target Location — не проверено), до 3 попыток. Резерв — постоянный модификатор максимума магии; состояние — SKSE co-save (`SCF4`/`SCPF` v1).
* Режим `bPersistentSummons`: длительность эффекта призыва продлевается, пока режим включён (обновление `ActiveEffect::duration`/`elapsedSeconds` у эффекта из `commandedActors`), призыв не исчезает по таймеру.
* Резерв магии вместо Spirit: постоянный модификатор максимума магии на время жизни постоянного призыва (через ActorValue modifier, снимается при отзыве); величина в INI.
* Авто-возрождение: после смерти — таймер 7 с (INI), «если другие призывы не умирали за последние N с» как в PoE2; затем тихое повторное применение того же заклинания призыва от игрока (`CastSpellImmediate`, без затрат), привязка нового актора к тому же слоту реестра (ордер и роль сохраняются).
* Сохранение/загрузка: состояние «постоянный призыв + заклинание» в SKSE co-save; после загрузки призывы восстанавливаются.
* **Готово, когда:** призыв живёт > 10 минут, погибший возвращается через 7 с в тот же слот строя, после сохранения/загрузки отряд на месте, резерв магии снимается при отзыве.

### M5. Размер армии
**Статус 2026-11-11:** строй — сделан (кольца по 6 слотов, внешнее заполняется первым, 1–4 призыва стоят как раньше, равномерное расширение до `fFormationMinSlotDistance`; настройки `[Squad] uFormationRingCapacity / fFormationInnerRingScale / fFormationMinSlotDistance / fFormationMaxExpansion`). Исследование лимита (по заголовкам CommonLibSSE-NG, без дизассемблера): ФАКТ — роспись движка `MiddleHighProcessData::commandedActors` (запись `{ActorHandle, ActiveEffect*}`), точка перков `BGSEntryPoint::kModCommandedActorLimit = 68` (вычисление `HandleEntryPoint`, id 23073), эффект `SummonCreatureEffect`. ГИПОТЕЗА — лимит = 1 + сумма значений точки 68 на кастере, вычисляется при касте, при переполнении снимается самый старый эффект. Следующий шаг — дизассемблировать на 1.5.97 места с `HandleEntryPoint(68)` и `SummonCreatureEffect::Start` и выбрать хук вычисленного лимита. Не сделано: подъём лимита движка, замер FPS. Найден дефект реестра SCF: «вытеснение» при `uMaxSummonsPerOwner` помечает старую запись `Displaced`, но следующий тик снова делает её `Active` (`RegisterSummon` обновляет существующую запись) — лимит SCF фактически не действует; исправлять вместе с лимитом движка.
* Исследование: где движок ограничивает число призывов (перки вида Twin Souls, проверка при касте эффекта призыва), можно ли поднять лимит перком/патчем значения без ESP.
* `uMaxSummonsPerOwner` (уже есть в реестре) становится реальным лимитом; строй масштабируется на 6–10 слотов (кольца).
* Замер производительности: 4/6/8/10 призывов в бою (кадры, длительность тика SCF в логе).
* **Готово, когда:** 6 призывов одновременно без вытеснения, FPS-просадка задокументирована в TESTING.md.

### M6. Панель миньонов (HUD)
**Статус 2026-11-11:** отображение сделано, по умолчанию скрыто (`[MinionPanel] bShowMinionPanel = false`, переключатель в FLICK «Show Minion Panel» и клавиша `uMinionPanelToggleKey`), ждёт полевого теста. Окно FLICK `IWindow` (HUD, ввод проходит в игру, скрыто в меню); снимок собирается на главном потоке в тике, отрисовка — из копии под мьютексом. Строка: имя, здоровье (полоса + числа), приказ | состояние | агрессия, цель, кулдаун команды, длительность. Не сделано: выбор подгруппы кликом, таймер возрождения M4 на панели.
* Оверлей через FLICK/ImGui: значок по типу, полоска здоровья, текущий приказ/состояние FSM, таймер возрождения, режим агрессии.
* Клик/горячая клавиша выбирает подгруппу для команд (основа для «вы — туда, ты — сюда»).
* **Готово, когда:** панель обновляется в реальном времени, не мешает UI игры и выключается из меню.

## 6. Риски и зависимости
* **M0 не решится отпуском радиусов** → понадобится подмена пакета или собственный обработчик движения (дороже, но APMF доказывает, что «отказ на источнике» в пакетной системе возможен).
* **Возрождение повторным кастом** может конфликтовать с модами на призывы (собственные скрипты призыва). Нужен режим «только ванильные заклинания призыва» и чёрный список.
* **Количество призывов**: производительность и пути в узких местах — главный ограничитель «армии».
* **AE 1.6.1170**: каждый новый адрес — отдельно для SE и AE, как требует проект.
