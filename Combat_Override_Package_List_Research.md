# Исследование: Combat Override Package List для Summon Control Framework

> **Документ:** исследовательское дополнение к `PLAN.md`  
> **Дата:** 10 ноября 2026 года  
> **Статус:** исследование механизмов Creation Kit и план игрового прототипа  
> **Цель:** проверить, можно ли использовать `Combat Override Package List` и `Procedure: HoldPosition` для ограничения дистанции, на которую призванное существо удаляется от владельца во время боя.

---

## 1. Краткий вывод

`Combat Override Package List` — перспективный механизм для первой версии ограничения боевого радиуса призывов. Skyrim уже использует похожую схему для штатных компаньонов: в `DialogueFollower` у follower alias настроен Combat Override со специальными `HoldPosition`-пакетами для интерьеров и открытого мира. Эти пакеты задают боевую `Location`, связанную с игроком, и позволяют компаньону продолжать сражаться в рамках собственного `Combat Style`.

Однако `HoldPosition` **не является жёстким leash**:

- он задаёт область, около которой актёр должен вести бой;
- он не гарантирует, что актёр немедленно прекратит преследование при выходе за радиус;
- по практическому описанию реализации, уже захваченная цель может удерживать актёра вне области, а проверка положения может происходить на переходах Combat State;
- `HoldPosition` не следует считать автоматической командой возврата к игроку.

Поэтому предлагаемая роль механизма в SCF:

1. **Первый backend для мягкого Combat Leash** — ограничивать типичное преследование, не заменяя штатный боевой AI.
2. **Не заменять им Follow AI** — следование вне боя остаётся отдельной системой.
3. **Не считать его аварийным возвратом** — для принудительного разрыва боя и возвращения нужен отдельный механизм.
4. **Сравнить с APMF Pursuit Leash / Combat Approach** — это альтернативные или дополняющие механизмы, но нельзя одновременно отдавать им контроль над одной и той же частью движения без проверки приоритетов.

**Рекомендация:** сделать небольшой ESP/ESL-прототип на одном ванильном призыве, прежде чем писать SKSE-интеграцию. Сначала проверить фактическое поведение `DialogueFollower`-подобного `HoldPosition` на призванном существе.

## 2. Что такое Combat Override Package List

Вкладка AI Packages у Actor Base содержит несколько специальных Override Package Lists. Они соответствуют отдельным Interrupt Behaviors, например:

- Spectator Override;
- Observe Dead Body Override;
- Guard Warn Override;
- Combat Override.

`Combat Override Package List` используется для замены штатного interrupt-поведения актёра во время боя. Если для Combat Override список не задан, движок использует стандартное боевое поведение, управляемое в том числе `Combat Style`.

Combat Override List — это `FormList` с AI Packages. Список проверяется сверху вниз; выбирается первый пакет, условия которого выполняются. Поэтому порядок записей является частью логики, а не просто порядком отображения.

### 2.1. Как создать Combat Override Package

В Creation Kit:

1. Создать новый AI Package.
2. Установить `Interrupt Override = Combat`.
3. Настроить `Package Template` и `Public Package Data` либо собственный `Procedure Tree`.
4. Добавить нужные Conditions.
5. Создать `FormList` и добавить в него Combat Override Packages в требуемом порядке.
6. Назначить FormList в поле `Combat Override Package List`.

Важное уточнение: `HoldPosition` — это **Procedure**, используемая внутри Combat Override Package. Не следует описывать его как отдельный Package Template. Для простого leash нужен Combat Override Package с Procedure Tree, в котором задействована `Procedure: HoldPosition`.

### 2.2. Порядок пакетов

Рекомендуемый порядок FormList:

1. Специальные условные боевые действия, которые действительно должны иметь приоритет (если они понадобятся, например, особая реакция или поддержка союзника).
2. `HoldPosition` как основной боевой режим.

Если пакет `HoldPosition` безусловно подходит всегда и стоит выше остальных, нижние пакеты могут никогда не получить управление. У каждого пакета должны быть обдуманные Conditions.

Для первого прототипа лучше не добавлять дополнительные боевые действия: оставить один `HoldPosition` и проверить его отдельно.

## 3. Что делает Procedure: HoldPosition

`HoldPosition` — специальная Procedure для Combat Override. Её входной параметр — `Location`.

Она позволяет актёру сражаться около указанной Location, используя собственный `Combat Style`. Это отличает её от обычных перемещающих Procedures.

### 3.1. Location

Для SCF интересна Location, центрированная относительно игрока. В практических руководствах по `DialogueFollower` отмечается, что штатный follower alias использует Combat Override с `Hold Position` пакетами для интерьеров и внешнего мира, настроенными так, чтобы компаньон не уходил слишком далеко от PC.

Для прототипа следует изучить оригинальные записи из `Skyrim.esm`, а не вводить радиус наугад:

- открыть `DialogueFollower` в xEdit;
- найти follower alias;
- проверить его `Combat Override Package List`;
- открыть обе записи Hold Position, используемые для разных типов локаций;
- зафиксировать `Location`, радиус, Conditions и порядок FormList;
- повторить эту конфигурацию в тестовом плагине и затем менять только один параметр за раз.

Не следует заранее считать, что отдельная ссылка на PlayerRef и любое значение Radius будут одинаково работать во всех типах ячеек. В частности, нужно проверить разрешение player-centered Location при переходе между интерьером и экстерьером.

### 3.2. Мягкость ограничения

Практическое исследование HoldPosition описывает следующие особенности:

- актёр обычно старается вести бой в назначенной области;
- если противник находится за границей, актёр может двигаться к границе и не иметь возможности атаковать;
- если актёр уже вступил в бой с конкретной целью, он часто продолжает с ней сражаться и за пределами Location;
- возврат к Location не следует считать мгновенным или гарантированным;
- для принудительного перемещения из опасной зоны автор практического исследования использовал бы отдельную перемещающую Procedure, например `Travel`.

Для SCF это означает, что `HoldPosition` — **soft leash**, а не строгая геометрическая граница.

### 3.3. Почему не следует использовать Travel как обычный Combat Leash

`Travel` и другие физические перемещающие Procedures способны перехватить штатное боевое поведение на время выполнения. Практические тесты Combat Override указывают, что актёр с активным Travel может продолжать движение к цели пакета, не атакуя даже при получении ударов.

Это противоречит нашей цели: суммон должен продолжать сражаться, но не уходить далеко от игрока.

Поэтому:

- `HoldPosition` — основной кандидат для штатного боя внутри области;
- `Travel` — только возможный инструмент отдельной команды отступления/возврата, а не постоянный leash;
- возвращение после выхода из боевой зоны нужно проектировать как отдельный переход FSM и отдельно проверять.

## 4. Как Skyrim применяет Combat Override

Есть два основных места назначения Override Package List.

### 4.1. Actor Base

Combat Override List можно назначить непосредственно Actor Base в AI Packages.

Плюсы:
- просто создать в CK;
- не требуется динамическое управление Alias;
- удобно для раннего эксперимента на специально созданном тестовом NPC.

Минусы:
- настройка относится ко всем экземплярам соответствующей базовой формы;
- она может быть перекрыта или заменена механизмами, связанными с Quest Alias;
- нельзя безопасно применять её к общей базе, если от неё создаются как дружественные, так и вражеские экземпляры.

**Использование в SCF:** только для изолированного тестового актора, не как окончательный способ назначения списка всем призывам.

### 4.2. Quest Alias

Quest Alias может предоставлять актёру собственный набор Package Data и Override Package Lists. Это позволяет ограничивать действие SCF конкретными зарегистрированными экземплярами, а не всей базовой формой.

Для SCF это предпочтительный кандидат:

- Quest работает как контейнер регистрации;
- Alias заполняется ссылкой на призыв, который прошёл проверку `SummonRegistry`;
- в Alias назначается Combat Override Package List SCF;
- при удалении призыва или потере регистрации Alias очищается.

Нужно различать два механизма Alias Package Data:

1. **Package Data / ALPC** — дополнительный package stack, который может сосуществовать с package entries других Alias.
2. **Override Package Lists** — отдельные поля, заменяющие соответствующие override lists базового актора, когда Alias активен.

Нельзя автоматически переносить выводы о добавочном характере ALPC на `Combat Override Package List`. Их совместимость и разрешение нескольких активных Alias должны быть проверены отдельно.

### 4.3. Приоритет Quest

Quest priority влияет на разрешение конфликтов пакетов, которые приходят через Alias. В практических исследованиях наблюдается, что более приоритетный Quest может перехватывать управление актёром у другого follower framework.

Не следует без проверки задавать SCF priority `100` или использовать универсальное правило вроде «83 достаточно для всех модов».

Перед выбором priority:

1. проверить priority `DialogueFollower`;
2. проверить распространённые follower frameworks из тестового load order;
3. выяснить, какой Quest/Alias уже назначает пакеты тестовому актёру;
4. выбрать минимальный priority, достаточный для конкретной схемы;
5. логировать конфликты и не пытаться бесконечно повышать priority.

Если в одном актёре уже есть Alias от другого мода, нужно выяснить, складываются ли его обычные Package Data и конфликтуют ли его Override Package Lists.

## 5. Предлагаемая реализация для SCF

### 5.1. Этап A — ESP/ESL proof of concept

На этом этапе не нужен SKSE DLL.

Создать тестовый плагин со следующими записями:

- `SCF_TestQuest` — тестовый Quest;
- `SCF_TestSummonAlias` — Reference Alias для тестового призыва;
- `SCF_CombatHoldPosition` — Combat Override Package;
- `SCF_CombatOverrideList` — FormList с этим пакетом.

Package:

- `Interrupt Override = Combat`;
- Procedure Tree с `Procedure: HoldPosition`;
- `Location` — player-centered, скопированная по смыслу из ванильного `DialogueFollower`;
- условия — только необходимые для запуска теста;
- без `Travel`, `UseWeapon`, `UseMagic` и дополнительных Simultaneous-веток.

Сначала испытать на одном тестовом актёре. После подтверждения назначения пакета проверить, работает ли тот же механизм на настоящем vanilla summon, чья форма и жизненный цикл отличаются от обычного follower.

### 5.2. Этап B — динамическое назначение зарегистрированным призывам

Если Alias PoC работает:

- создать ограниченный пул Alias под максимальное поддерживаемое количество одновременных призывов;
- при регистрации призыва выделять свободный Alias;
- заполнять его ссылкой на актёра;
- при исчезновении, смерти или диспеле очищать Alias;
- при загрузке сохранения восстанавливать регистрацию и Alias;
- предотвращать одновременное назначение одного призыва нескольким слотам.

Для первого варианта можно использовать Papyrus для заполнения/очистки Alias. Если потребуется более надёжная нативная интеграция, исследовать SKSE/CommonLib API для работы с Quest/Alias. Не считать динамическое назначение Alias через нативный код готовым, пока не проверены жизненный цикл и сохранения.

### 5.3. Этап C — несколько профилей дистанции

Для статических профилей можно создать несколько FormList/Package вариантов:

| Профиль | Назначение |
|---|---|
| Close | Призыв держится ближе к владельцу |
| Standard | Обычная боевая дистанция |
| Wide | Разрешено более свободное преследование |

Конкретные значения Radius нужно получить из тестов и сравнения с ванильными follower packages. Не фиксировать 1000/2000/3000 как проверенные значения до испытаний.

Если потребуется произвольный MCM-слайдер, Combat Override List сам по себе не предоставляет прямого динамического числового API. Возможные пути:

1. переключение между заранее созданными профилями;
2. отдельный SKSE-механизм, который меняет runtime-параметр после исследования соответствующих структур;
3. APMF `Pursuit Leash` или `Combat Approach` как отдельный динамический backend.

Последние два варианта требуют runtime-проверки и не должны смешиваться с Package control без заранее определённой схемы владения движением.

## 6. Связь с APMF

APMF предоставляет отдельные AI facets, включая:

- `Pursuit Leash` — ограничение преследования относительно anchor;
- `Combat Approach` — управление сближением с актёром во время боя.

Это не то же самое, что CK `Combat Override Package List`.

Предлагаемое разделение:

| Механизм | Предполагаемая роль |
|---|---|
| Combat Override + HoldPosition | Ванильный мягкий leash, сохраняющий Combat Style |
| APMF Pursuit Leash | Альтернативное/дополнительное ограничение преследования через SKSE backend |
| APMF Combat Approach | Контроль сближения с целью |
| SCF FSM | Решение, когда суммон должен сражаться, отступать или возвращаться |
| Catch-Up Warp | Аварийное восстановление после застревания/критического отставания |

**Не следует одновременно включать HoldPosition, Pursuit Leash и Combat Approach на одном актёре без тестов.** Несколько механизмов могут ограничивать одну и ту же часть движения. Нужно заранее решить, какой backend владеет leash в текущем режиме.

APMF описывает арбитраж по отдельным facets и сообщает, кто владеет каждым аспектом поведения. В актуальных заметках проекта также упоминается взаимодействие Combat Approach с package HoldPosition, но соответствующая уступка package leash описана как ещё не проверенная в игре. Поэтому совместимость должна быть отдельным тестом, а не архитектурным предположением.

## 7. Известные ограничения и риски

| Риск | Почему важен | Проверка/смягчение |
|---|---|---|
| HoldPosition — мягкий leash | Суммон может продолжить бой за пределами Location | Проверять текущую цель и расстояние в бою; не считать максимальный радиус жёстким |
| Не происходит автоматического возврата | HoldPosition удерживает боевую область, а не обязательно запускает Follow | Отдельный переход FSM после потери/сброса цели |
| Travel подавляет боевое поведение | Суммон может перестать атаковать, пока перемещается | Не использовать Travel как постоянный боевой leash |
| Package может зафиксировать актёра | Неправильный Procedure Tree или входные данные могут дать freeze | Начать с одного HoldPosition, избегать Simultaneous до отдельного теста |
| Потеря Combat Style | Физические Procedures вроде UseWeapon могут заменить штатный боевой AI | Не добавлять UseWeapon/UseMagic в базовый leash без необходимости |
| Конфликт Quest Alias | Другой мод может назначать свои пакеты | Проверять Quest priority, aliases и текущий пакет |
| Вражеские призывы затронуты | Actor Base общий для дружественных и враждебных экземпляров | Для production предпочесть Alias, заполняемые только SummonRegistry |
| Интерьер/экстерьер | Ванильный follower использует разные пакеты для разных условий | Сначала исследовать обе ванильные записи и повторить их условия |
| Save/load и cell unload | Alias и actor references могут менять состояние | Обязательные тесты unload/load, смерть, диспел, сохранение |
| Конфликт с APMF | Два backend могут одновременно ограничивать движение | В каждый момент один владелец leash; интеграционный тест |

## 8. План экспериментов

### Experiment 1 — изучить ванильный эталон

- [ ] Открыть `Skyrim.esm` в xEdit.
- [ ] Найти Quest `DialogueFollower`.
- [ ] Найти Alias активного follower.
- [ ] Зафиксировать `Combat Override Package List`.
- [ ] Найти FormList и все входящие в неё PACK записи.
- [ ] Изучить `Interrupt Override`, Procedure Tree и `Procedure: HoldPosition`.
- [ ] Зафиксировать player-centered Location, тип Location и Radius.
- [ ] Сопоставить пакеты для interior и exterior.
- [ ] Сохранить FormID, EditorID и скриншоты записей в документацию SCF.

**Результат:** воспроизводимая спецификация ванильной схемы, а не догадки по названию пакета.

### Experiment 2 — проверить HoldPosition на тестовом NPC

- [ ] Создать тестовый Combat Override Package с одной Procedure `HoldPosition`.
- [ ] Установить `Interrupt Override = Combat`.
- [ ] Назначить FormList тестовому NPC через Actor Base.
- [ ] Проверить бой с врагом внутри Location.
- [ ] Проверить врага за пределами Location.
- [ ] Проверить, продолжает ли NPC преследование уже выбранной цели.
- [ ] Проверить поведение при смене Combat State.
- [ ] Проверить melee, ranged и magic Combat Styles.

**Результат:** определить фактическое поведение HoldPosition и границы его enforcement.

### Experiment 3 — проверить Quest Alias

- [ ] Создать Quest с Reference Alias.
- [ ] Назначить Alias Combat Override Package List.
- [ ] Заполнить Alias тестовым NPC.
- [ ] Проверить, получает ли NPC пакет из Alias.

- [ ] Проверить приоритеты и текущий активный пакет.

**Результат:** выбрать надёжный per-reference способ назначения только управляемым призывам.

### Experiment 4 — проверить на настоящем Summon

- [ ] Проверить два одновременных summon.

**Результат:** доказать, что механизм применим к реальным временным призывам.

### Experiment 5 — проверить конфликт с APMF

- [ ] Запустить только Combat Override HoldPosition.
- [ ] Запустить только APMF Pursuit Leash.
- [ ] Запустить только APMF Combat Approach.

**Результат:** определить, использовать ли Combat Override и APMF вместе или как взаимоисключающие backend-профили.

## 9. Приёмочные тесты

- [ ] Суммон в бою обычно остаётся в пределах настроенной player-centered Location.
- [ ] Суммон продолжает использовать собственный Combat Style.
- [ ] Суммон атакует врагов внутри области.
- [ ] Если враг находится далеко за пределами области, суммон не должен безусловно убегать за ним через всю локацию.
- [ ] Поведение при уже установленной цели за границей документировано отдельно.
- [ ] После завершения боя штатный Follow возвращает суммон к владельцу.
- [ ] Combat Override не влияет на вражеские призывы.
- [ ] Пакет не блокирует атаки, заклинания или анимации на постоянной основе.
- [ ] Поведение корректно в interior и exterior.
- [ ] Смерть/диспел/удаление суммона очищает Alias.
- [ ] Save/load не оставляет актёра с активным SCF Override без регистрации.
- [ ] Отключение функции возвращает стандартный Combat AI.

## 10. Решение для текущей архитектуры SCF

На текущем этапе принять следующий дизайн:

1. `CombatOverrideBackend` — отдельный backend для мягкого боевого ограничения дистанции через CK FormList и `HoldPosition`.
2. Основной production-путь — Alias-based назначение только зарегистрированным суммонам; Actor Base использовать для тестового NPC и диагностики.
3. `HoldPosition` не является заменой `FollowOwner`, `PursuitLeash`, `CatchUpWarp` или FSM `Return`.
4. Сначала доказать работоспособность статического радиуса и правильного player-centered Location.
5. Только после PoC делать динамические радиусы, MCM и нативное управление Alias.
6. APMF Pursuit Leash и Combat Approach оставить отдельными backend-экспериментами; не допускать неконтролируемого одновременного управления одним movement facet.

## 12. Ключевой вывод

`Combat Override Package List` — реальный ванильный механизм, который стоит исследовать до разработки собственного боевого leash. `DialogueFollower` даёт готовый образец player-centered `HoldPosition` для компаньонов.

Но `HoldPosition` нужно считать **мягким ограничителем боевой области**, а не надёжной системой жёсткого возврата. Наиболее безопасная стратегия для SCF — сначала скопировать и проверить ванильный принцип на тестовом призыве, затем назначать Override через Alias только зарегистрированным призывам и лишь после этого решать, нужен ли APMF или собственный SKSE movement controller для строгого ограничения расстояния.

## 13. Решение после полевых тестов (2026-11-10): Combat Override не используется

К этому разделу проект пришёл после того, как `SummonMovement` уже двигал суммонов, но поведение оставалось «двойным»: игрок видел, что суммон одновременно пытается исполнять приказ и собственный AI-паттерн.

### 13.1. Что показал полевой лог

* `StartCombat` при приказе `FocusTarget` возвращает управление, но суммон, оставаясь в бою, не атакует: его ванильная логика commanded-actor (следование за владельцем) продолжает владеть поведением. Приказ `Attack` при этом остаётся активным, то есть это не ошибка очереди команд.
* В `Passive`-режиме `StopCombat()` вызывается на каждом такте, но движок тут же снова втягивает суммона в бой — «два паттерна» борются каждый кадр.
* `Return` работает только потому, что движение перехватывается keep-offset'ом; бой при этом не запрещён на уровне движка, и суммон может повторно втянуться в драку по дороге.

Вывод: для требований «в `Passive` не атаковать ни при каких обстоятельствах» и «до игрока — без боя» нужен **запрет боя на уровне движка**, а не мягкий leash.

### 13.2. Почему здесь не подходит Combat Override + HoldPosition

| Требование SCF | Combat Override + HoldPosition |
|---|---|
| Запретить любой бой в `Passive` | Не может: HoldPosition сохраняет боевой AI и Combat Style, враг внутри области всё равно атакуется |
| Выйти из боя по команде `Return` | Не может: HoldPosition ограничивает область, а не запрещает бой; уже захваченная цель удерживает актёра |
| Атаковать только назначенную цель | Не может: выбор цели остаётся за движком |
| Работает без ESP/ESL | Нет: нужны пакеты, FormList, квест и alias |
| Управление на каждый приказ | Нет: статический набор пакетов, переключение только между профилями |

Дополнительно: механизм требует отдельного плагина с пакетами и Alias-пула, то есть усложняет поставку мода, а по документации остаётся «мягким» (раздел 3.2). Поэтому весь план экспериментов 1–5 из раздела 8 для SCF **не выполняется**; он остаётся справочным материалом для будущего отдельного backend-профиля, если понадобится именно боевой leash с сохранением ванильного Combat Style.

### 13.3. Принятая архитектура: Combat Gate (StartCombat denial seat)

Полный контроль над боем реализован без ESP, на уровне SKSE (`src/Engine/CombatGate.cpp`):

1. **Запрет входа в бой.** Патч **точек вызова** `Actor::StartCombat` (`RELOCATION_ID(37608, 38561)`, SE 1.5.97 → `SkyrimSE.exe+6251B0`): скан `.text` находит 10 сайтов (9 × `call`, 1 × `jmp`-обёртка), каждый переписывается на thunk, а thunk вызывает реальную функцию по её адресу (вход не трогается). Для зарегистрированного суммона вызов отклоняется (`return false`, как это делает движок для мёртвого `self`), если его текущая `CombatPolicy` не разрешает бой. При приказе `FocusTarget` разрешён ровно один актор — назначенная цель. Подробности и полевое падение из-за ошибочного «хука на вход» — `ARCHITECTURE.md` §21.2.
2. **Запрет атаки как таковой.** Пока бой запрещён, выставляются нативные биты `Actor::BOOL_FLAGS::kAttackingDisabled | kCastingDisabled` (тот же приём, что APMF документирует как wholesale deny). Это гарантирует `Passive` даже если бой каким-то путём уже идёт.
3. **Разрыв текущего боя.** При смене политики на «нельзя» вызывается `StopCombat()` с очисткой `currentCombatTarget` и `CombatController`.
4. **Движение остаётся за `SummonMovement`** (раздел 20 ARCHITECTURE.md): keep-offset, слоты строя, возврат и подход к цели.

Матрица `CombatPolicy` (`src/Core/CombatPolicy.cpp`):

| Состояние | `allowCombat` | `restrictToTarget` | `disableAttacks` |
|---|---|---|---|
| `Passive` (любой приказ) | нет | — | да |
| `Return` | нет | — | да |
| `MoveTo` с точкой | нет | — | да |
| `Attack` + живая цель | да | да (только цель) | нет |
| `Attack` без цели | нет | — | да |
| `WaitGuard` / `Follow` | да | нет | нет |

Итог: у суммона больше нет «второго паттерна». Он либо исполняет приказ (движение, следование, охрана), либо бой, разрешённый политикой, — но не оба одновременно. `Combat Override Package List` для этого не нужен; документ остаётся описанием отклонённой альтернативы и её ограничений.
